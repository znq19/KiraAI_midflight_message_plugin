# 随时插话（Midflight Inbox）

**一句话说明**：bot 正在连续干活（调用工具）的时候，你中途发的消息不用排队等下一轮——它会在下一个工具边界"搭车"进入当前对话，bot 马上就能看到并回应；还可以用"停"即时直接强制叫停（需手动开启，但不开启也可以沟通让TA明白该停了）。

## 30 秒效果示例

```
你:   @bot 把这个文件夹里 50 张图按内容分类整理
bot:  收到，我先看看都有什么~        ← bot 开始连续执行（比如要跑 10 步）
你:   顺便按拍摄时间排个序           ← 【以前】这句话要等全部干完才被看到
                                    ← 【现在】下一个工具边界就流入当前轮
bot:  好嘞，排个序👌               ← bot 边干活边接住你的话，继续执行
...   全程不重启、不打断，任务带着新要求一次做完
```

想强制叫停？在配置里打开「启用停止词」（**默认关**），然后：

```
你:   停，不用做了
bot:  （下一个工具边界即停止后续步骤，已完成的部分保留，随时可以接着聊）
```

## 安装方法（二选一）

**方法一：WebUI 上传（推荐）**

1. 把本插件整个文件夹打成 zip（`manifest.json` 要在 zip 根目录）；
2. 打开 KiraAI WebUI → 插件 → 上传/安装，选择这个 zip；
3. 在插件列表启用即可，默认配置直接能用。

**方法二：手动放置**

1. 把 `midflight_message_plugin` 文件夹整个复制到 `data/plugins/` 下；
2. 重启 KiraAI 或在 WebUI 插件页重载；
3. 在插件列表确认已启用。

> 本插件无任何第三方依赖（requirements.txt 为空），不需要装额外包。
> 要求 KiraAI 核心版本 **>= 2.29.7**。

## 工作原理（一图流）

```
你中途发消息（bot 正在连续执行中）
   │
   ▼
聊天插件（default-chat / S版 / Z版）照常防抖、合并
   │        ※ 本插件不改任何消息的策略
   ▼
两条流入通道，谁先到达走哪条：
   │
   ├─ 通道①：消息还在缓冲区
   │     bot 每次工具调用返回时，本插件看一眼该会话的缓冲区(buffer)：
   │        ├─ 命中停止词？→ 停掉本轮后续步骤（不注入）      【停止词默认关】
   │        ├─ 通过过滤？  → 以原生聊天样式追加进工具结果文本
   │        │              下一次 LLM 调用直接读到 → bot 自然回应
   │        └─ 不通过？    → 原样放回缓冲区，走聊天插件正常开新轮
   │
   └─ 通道②：消息已被防抖 flush 成批次（v1.2.4 新增）
         若批次到达时该会话正在跑（如 S版 QueueMerge 本想把它扣进队列），
         本插件以最高优先级先截住：消息转入流入队列，掐掉批次，
         下一个工具边界照样注入——不会再排队到本轮结束。
         （未通过过滤的消息放回缓冲区；QueueMerge 自己重推的批次绝对放行）
                                    │
兜底去重：已流入的消息若又被合并成新批次 ▼
   → 整个批次全部是已消费消息时，掐掉，防止重复回复
```

赶不上边界也没关系：如果 bot 那一步之后不再调工具，消息照常由聊天插件开新一轮，行为和没装本插件完全一样——**没有任何消息会被卡住或丢掉**。

### 停止词（⚠️ 默认关闭）

| 你想… | 改这个 | 默认值 |
|---|---|---|
| 能发"停"来叫停 bot 当前这轮 | **启用停止词（默认关，要用请手动打开）** | **关** |
| 改叫停用的词 | 停止词列表 | 停/停止/取消/别做了/停下/stop/cancel |
| 必须整句正好是"停"才算（防误伤） | 停止词匹配方式 = exact | contains（包含即命中） |

> 说明：停止只停"还没发生的步骤"，当前已发出的文字不会撤回；已做完的进度和上下文都保留，之后正常继续聊即可。

| 你想… | 改这个 | 默认值 |
|---|---|---|

| 只有指定的人才能中途插话 | 启用用户白名单 + 允许流入的用户 ID | **白名单默认关** = 所有群友都能流入 |

### 数量与时间窗口（默认折叠，不用动）

| 你想… | 改这个 | 默认值 |
|---|---|---|
| 限制一轮最多流入几条 | 单轮最多流入条数 | **0 = 自动沿用系统"最大消息缓冲条数"** |
| 太旧的消息不要流入 | 流入消息新鲜度（秒） | **-1 = 不限（默认，推荐）**；0 = 自动沿用系统"最大消息合并间隔" |
| 超长消息截断 | 单条流入最大长度 | 0 = 不限 |
| 某些内容（正则）永不流入 | 内容正则黑名单 | 空 |

### 媒体流入（默认全开，不用动）

语音、图片、文件这些"参考素材"**都能流入**，而且用的是官方同一套转换：

| 你想… | 改这个 | 流入后 bot 看到 |
|---|---|---|
| 语音消息流入 | 允许语音消息流入（默认开） | `[Record 语音转文字]`（官方 STT） |
| 图片/表情包流入 | 允许图片/表情包流入（默认开） | `[Image 描述, file_path: …]`——bot 还能用文件工具**读原图** |
| 文件/视频流入 | 允许文件/视频流入（默认开） | 落盘带路径，bot 可**直接读原文件**（大小阈值跟随官方，当前官方硬编码 10MB，超限仅流入文件名提示） |
| 合并转发流入 | 允许合并转发流入（默认开） | 内容递归展开 |

> 转换所需的 VLM/STT 模型就是你在系统配置里已经配好的那些，无需额外设置。

### 注入格式 / 会话级覆盖（高级，99% 的用户不用碰）

- **自定义注入模板**：默认留空 = 和平时聊天一模一样的官方格式——`[时间] [message_id: xxx] [user_nickname: 昵称, user_id: xxx] | 内容`（群聊另带群名/群号，v1.2.4 起直接复用官方内置 kira-ai 插件的 `_format_user_message`，格式自动跟随官方），bot 感知不到差别，群聊里也能分清是谁、什么时候说的。只有当你用的模型对工具结果格式敏感时，才考虑自定义，可用变量 `{sender_nickname} {user_id} {message_id} {group_name} {group_id} {text} {time} {n}`。
- **按会话覆盖配置**：全局一套默认，个别群单独改。例：`{"qq:gm:123456": {"flow_method_group": "any"}}` = 只有这个群所有消息都流入，其他群不变。键支持 `qq:gm:*` 通配。**默认空，不配置完全不影响使用。**

## 常见问题 FAQ

**Q1：消息没有流入怎么办？**

按顺序自查：
1. 插件是否已启用（WebUI 插件页）；
2. bot 当时是不是真的在"连续调用工具"——如果它只是在生成一段话，没有工具调用，就没有可搭车的边界，消息会走正常的下一轮（这是设计如此，不是故障）；
3. 群聊默认 `all` 模式需要 @/回复/唤醒词/戳一戳 任一触发，纯围观聊天不会流入；
4. 如果你把「流入消息新鲜度」改成了具体秒数或 0（自动），消息可能因超过窗口被拒——默认 -1 不限时无此问题；
5. 打开「调试日志」再看一次，日志里会写明每条消息为什么没流入。

**Q2：停止词没反应？**

停止词**默认是关的**！先到「停止词」分组打开「启用停止词」。另外停止发生在"下一个工具边界"：如果 bot 已经没有后续工具调用（正在收尾），本轮本来就要结束，停止词不会有可见效果，这也是正常的。

**Q3：和 S版 / Z版 / 官方 default-chat 聊天插件冲突吗？**

不冲突。本插件不改任何消息的策略、不碰防抖和合并的参数：消息还在缓冲区时只在工具边界"借读"；若消息先被防抖合并成批次且会话正在跑，会在队列合并插件（S版/Z版的 QueueMerge，机制相同均已核实）把它扣进 pending 之前先截住转入流入（v1.2.4 起），QueueMerge 自己重推的批次（`_qm_self` 标记）则绝对放行。与 session_merger 的合并组串行队列也不冲突：它对被其它插件掐停的批次直接跳过（`is_stopped` 检查），且其延后重放的批次不会触发本插件误拦截（运行开始标记只在 `ON_LLM_REQUEST` 做，被拦停的批次走不到那一步）；它的跨会话控制批次（handoff/路由/旧版投递）本插件识别后绝对放行。唤醒词默认还会自动沿用你装的聊天插件的配置（Z版→S版→官方的顺序）。没过滤通过的消息会原样放回，由聊天插件照常处理。

**Q4：会不会重复回复？**

不会。每条流入的消息都会记录 message_id（保留 10 分钟）：如果它之后又被聊天插件合并成新批次，本插件会发现整个批次全是已消费消息并掐掉这一轮，保证"要么搭车流入、要么开新轮"，不会两次都发生。

**Q5：支持哪些平台？**

全平台通用（QQ / Telegram / Discord / 微信等），代码不写死任何平台。唯一例外：「戳一戳」是 QQ 专有功能，其他平台识别不到时会自动忽略、不报错，不影响其余功能。

**Q6：流入的消息 bot 看到的样式和正常聊天一样吗？**

一样。默认使用与官方完全相同的消息文本化方式，不包装、不改写，模型感知不到差别。

## 兼容性

- KiraAI 核心版本 **>= 2.29.7**（低版本拒绝加载）；
- 与 default-chat / S版 / Z版 聊天插件、KiraOS、SubAgent、MCP 工具插件等共存无冲突；
- **与 S版/Z版的媒体管线深度兼容**：它们的媒体控制（仅唤醒识别、占位符替换）在消息链层面生效，本插件"读到什么就原样流入什么"，其策略被完整尊重；并行媒体识别（VLM/STT 预处理）的结果会被官方文本化直接复用，**不会重复识别、重复计费**；v1.2.0 起还会把消息中的图片/语音/文件作为工具结果附件透传，即使系统开了 native 原生多模态模式，流入的图片也能带上可访问的文件路径；
- 已知边界（如实说明）：若恰好在 S/Z 版并行识别"占位符已替换、描述未填回"的秒级窗口内流入，该条媒体会以占位符形态被 bot 看到——不报错、不丢消息，完整内容仍会进入历史/下一轮；
- 停止时的 tool_calls 一致性由 KiraAI 官方机制保障；
- 纯第三方插件，不修改 KiraAI 本体任何文件。

- **修复流入消息缺少发送者信息的问题**：此前流入的是纯文本内容，缺少官方批次消息自带的时间、message_id、昵称、user_id（这些信息由官方内置 kira-ai 插件在 LLM 请求前拼装，群聊里 bot 靠它分清谁说的话）。现默认**直接调用官方内置 kira-ai 插件的同一个格式化函数** `_format_user_message`（自动跟随官方格式演进，永不漂移；取不到时用内置复刻版兜底），群聊/私聊/系统通知三种变体全部对齐
